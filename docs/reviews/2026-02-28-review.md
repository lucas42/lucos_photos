# Architectural Review: lucos_photos

**Date:** 2026-02-28
**Reviewer:** lucos-architect[bot]
**Commit:** c3be2c0

## Summary

The project has strong foundations. The API/worker separation is clean, the CLAUDE.md is unusually thorough, and the conventions around environment variables, Docker naming, and volume management are followed correctly. The project is early -- the worker is still a stub, there is no web UI, and no photos have been processed yet -- which makes this an ideal time to address structural questions before they become load-bearing.

## Strengths

- **API/worker separation** is clean, with well-defined boundaries documented in CLAUDE.md
- **Idempotent upload** with SHA256 deduplication is a sound design
- **Volume conventions** are followed correctly (explicit named volumes, all registered in configy)
- **Database schema** is sensible: UUID primary keys, normalised bounding boxes, the `person_confirmed` flag for distinguishing ML guesses from human verification
- **CI configuration** is correct and follows lucos conventions
- **Test infrastructure** uses SQLite in-memory with proper FastAPI dependency overrides

## Concerns

- **Container count.** Five containers (Postgres, Redis, Qdrant, API, worker) is a lot for a personal photo library. Qdrant was identified as removable (see #23 and ADR-0001), reducing this to four.
- **No docker-compose healthchecks** on any container. The API's `depends_on: postgres` only waits for the container to start, not for Postgres to be ready to accept connections. This is a reliability gap that will cause intermittent startup failures.
- **Module-level engine creation** in `database.py` forces environment variables to be set before import and creates a fragile test workaround. See #25.
- **Worker image size.** Once InsightFace is added, the worker image will be 1.5--2.5 GB. This will significantly impact build and deploy times via the `lucos/build-amd64` CI orb.
- **PhotoPerson join table** exists alongside the Face table, which already links photos to persons. The CLAUDE.md says it is for "direct links beyond face-derived ones" -- care is needed to avoid data consistency problems where a person is tagged via PhotoPerson but has no corresponding face record, or vice versa.
- **Auth model ambiguity.** M2M auth (CLIENT_KEYS) and user auth (lucos_authentication) are distinct flows that should stay separate, but there was no documentation clarifying whether the system is truly single-user or multi-user. This affects every subsequent endpoint design.
- **Incomplete upload pipeline.** The upload endpoint did not actually enqueue Redis jobs at the time of review.
- **No photo serving strategy decided.** Need to choose between API proxy and static file server (see #26).
- **Dependabot gaps.** No dependabot configuration for docker-compose image versions (Postgres, Redis). See #31.
